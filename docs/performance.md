# Performance Baseline — Order Execution Cycle

Baseline numbers for Soroban CPU instruction cost and memory usage across the
three core order execution scenarios. Generated by running:

```
cargo bench -p order-handler --bench order_execution
```

> **Note:** Benchmarks are excluded from CI (`cargo test`) because they are too
> slow for routine checks. Run them locally or in a dedicated perf job with
> `cargo bench -p order-handler --bench order_execution`.

### Metric Definitions

| Metric | How it is measured |
|--------|--------------------|
| CPU Instructions | `env.cost_estimate().budget().cpu_instruction_cost()` after a reset to default limits |
| Memory (bytes) | `env.cost_estimate().budget().mem_bytes_cost()` |
| DS Reads | manual count of `DataStoreClient::get_*` calls in the hot path |
| DS Writes | manual count of `DataStoreClient::set_*` / `add_*` calls |
| XC Calls | number of cross-contract invocations (oracle, vault, role_store) |

## Resource regression gate (CI)

`.github/workflows/resource-bench.yml` (issue #1064) reports Soroban resource
usage for core flows on every PR that touches contracts, libs or tests, on
pushes to `main`, and weekly. A material regression fails the job before merge.

**Harness:** `tests/resource_bench.rs` runs these scenarios in a fresh `Env`
and records the metered resources of each top-level invocation:

| Scenario | What it measures |
|---|---|
| `lifecycle/create_deposit`, `lifecycle/execute_deposit` | LP deposit |
| `lifecycle/create_order_increase`, `lifecycle/execute_order_increase` | Open a long |
| `lifecycle/create_order_decrease`, `lifecycle/execute_order_decrease` | Close it |
| `lifecycle/create_withdrawal`, `lifecycle/execute_withdrawal` | LP withdrawal |
| `bounds/create_orders_max_batch` | `create_orders` at `MAX_ORDER_BATCH_SIZE` |

Metrics per scenario: `instructions`, `mem_bytes`, `disk_read_entries`,
`memory_read_entries`, `write_entries`, `disk_read_bytes`, `write_bytes`,
`contract_events_size_bytes`, `fee_total_stroops` (SDK pubnet fee snapshot).

The values come from the Soroban cost model, not wall-clock time, so they are
deterministic for a given SDK and code; the harness test itself asserts two
runs are identical and that every scenario stays inside mainnet limits.
Contracts are registered natively, so Wasm VM costs are not included; read the
numbers as a stable relative signal, not absolute on-chain cost.

**Baseline and thresholds:** `docs/benchmarks/resource-baseline.json` holds the
recorded numbers and per-metric tolerances. A metric regresses only when it
exceeds *both* its absolute and percentage tolerance. Ledger-entry counts have
zero tolerance: one extra read or write fails the gate. Missing or new
scenarios also fail.

**Protocol-bound constants:** the baseline records the batch/length bounds
(`MAX_ORDER_BATCH_SIZE`, `MAX_PRICE_BATCH_SIZE`, `MAX_SWAP_PATH_LENGTH`, ...).
Raising one above its recorded value fails the gate until the baseline is
regenerated, so a bigger bound always ships with fresh benchmark evidence.

**Commands:**

```bash
make bench-resources                                  # run + compare against the baseline
make bench-baseline RATIONALE="why the numbers moved"  # rewrite the baseline
python3 scripts/test_bench_compare.py                 # unit tests for the gate
```

Baseline updates require `RATIONALE`; it is stored in the baseline's `meta`,
and CI rejects a PR that changes the baseline's numbers, thresholds or
constants without changing the rationale.
